What a page load actually costs

Field notes · 12 minute read

A page load is not one event but a negotiation between the network, the parser and the main thread. Each of the three can be the bottleneck, and which one wins changes with the shape of the document, the size of the scripts and the machine underneath.

The parser goes first

Before anything is painted the parser must reach the end of the critical markup. A single blocking script in the head is enough to hold the first paint for as long as it runs, which is why measurement tools report the first contentful paint separately from the load event.

The cost is not constant. The same script takes different time on different hardware, and on shared infrastructure that hardware is not known in advance.

Then the main thread

Work scheduled after the first frame does not move the first paint, but it does block input. Tools account for this as blocking time: the part of every long task beyond fifty milliseconds, summed over the window between the first paint and interactivity.

And finally layout

Content that arrives late moves what is already on screen. The metric for this is unitless and, on a stable page, close to zero, which makes it a poor candidate for relative comparisons and a good candidate for absolute thresholds.

ParseBlocking scriptsFirst Contentful Paint
RenderImage and font deliveryLargest Contentful Paint
InteractLong tasksTotal Blocking Time
SettleLate contentCumulative Layout Shift

Why one measurement is not a measurement

Any of these numbers moves between runs on the same machine, and moves further between machines. A threshold applied to a single run therefore answers a question nobody asked: whether this particular load, on this particular machine, crossed a line.

Written for the perfgate demo corpus. No trackers, no fonts, no frameworks.
